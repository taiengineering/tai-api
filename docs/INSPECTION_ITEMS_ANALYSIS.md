## 1. 현재 상태 요약

```
[inspection_master]          →  (연결 없음)  →  [inspection_set_items]  →  [safety_inspection_results]
  772개 상세 항목                                  67개 "점검 의무" 항목          실제 점검 기록
  113개 설비 유형                                   master_item_id = 0 (전부)     → 결과 저장
  4개 섹터                                          "점검 의무 (법 제X조)" 수준
  GPT가 법령에서 추출                                법령엔진이 자동 생성
```

**핵심 발견: 파이프라인이 끊겨 있다.**

- `inspection_master`: 772개 상세 점검 항목 (설비별 5~12개씩) — **이미 존재**
- `inspection_set_items`: 67개 "점검 의무" — 법 조항 단위 BOOLEAN 체크만
- `inspection_set_items.master_item_id`: 67건 전부 NULL — **연결 없음**

## 4. 문서 엔진과의 관계

### 4.1 document_forms의 required_fields vs inspection_master

| document_forms의 필드 | 유형 | inspection_master 매핑 |
|----------------------|------|----------------------|
| inspection_done (점검 실시 여부) | 메타데이터 | safety_inspections.status_code ✅ |
| inspection_datetime (점검일시) | 메타데이터 | safety_inspections.inspection_date ✅ |
| inspector (점검자) | 메타데이터 | safety_inspections.inspector_id ✅ |
| abnormal (이상 여부) | 결과 요약 | safety_inspection_results 집계 ✅ |
| action (조치사항) | 결과 상세 | safety_inspection_results.note ✅ |
| **equipment_check (설비 점검)** | **체크리스트** | **inspection_master → 연결 필요** |
| **electrical_check (전기 점검)** | **체크리스트** | **inspection_master → 연결 필요** |
| **scaffold_check (비계 점검)** | **체크리스트** | **inspection_master → 연결 필요** |

**결론:** 메타데이터는 이미 수집 완료. 체크리스트 항목이 연결되지 않은 것이 문제.

### 4.2 문서 출력 시 필요한 구조

```
문서: DOC-BLD-002 (소방시설 점검기록)
  ↓ required_fields에서 "target", "result", "defect", "action" 필요
  ↓ 실제 데이터는 safety_inspection_results에 있어야 함
  ↓ safety_inspection_results의 항목 = inspection_set_items
  ↓ inspection_set_items ← inspection_master에서 가져와야 함
  
현재: inspection_set_items = "점검 의무 (소방시설법 제22조)" 1건
필요: inspection_set_items = "수신기 전원", "감지기 작동", "스프링클러 헤드" 등 5~8건
```

| 앱 점검 화면 (worker-check) | 1건 체크 | 설비별 5~12건 체크 | ★★★★ |

### 5.2 작업자 체감 변화

```
[현재] 소방시설 점검:
  ☐ 점검 의무 (소방시설법 제22조) → Yes
  → 끝 (1초)

[변경 후] 소방시설 점검:
  ☐ 수신기 전원 표시등 정상
  ☐ 감지기 작동 시험
  ☐ 스프링클러 헤드 외관

  → 5~8건 (30초~1분)
```

**하지만 이것이 TAI Safe의 핵심 가치입니다.**
"진짜 점검을 했는지"를 기록하는 것. "점검 했다"에 체크만 하는 건 의미 없음.

## 6. 해결 전략

### 6.1 단계적 접근 (추천)

**Phase 1: 연결 파이프라인 구축** (1일)
- 회사가 설비를 등록하면(`equipment_assets`) → 해당 설비의 `equipment_std`와 매칭되는 `inspection_master` 항목을 자동으로 `inspection_set_items`에 복사
- `inspection_set_items.master_item_id`로 원본 연결

**Phase 2: 기존 67건 처리** (반일)
- 기존 "점검 의무" 항목은 유지 (법적 의무 기록용)
- 새 상세 항목은 별도 세트로 추가 (설비별 점검 세트)

**Phase 3: 앱 점검 화면 수정** (Cursor)
- worker-check.html: 설비별 상세 항목 표시
- 정상/이상/보류 3단 선택 (현재와 동일 UX)
- 이상 시 메모+사진 (현재와 동일)

**Phase 4: 문서 연결** (문서 엔진)
- inspection_fetcher가 상세 항목별 결과를 가져와 문서 렌더링

### 6.2 최소 체크 원칙과의 균형

- **필수 항목만 기본 표시** (4~6개)
- **권고 항목은 "더보기"로 접기** (나머지 2~6개)
- **주기별 자동 필터링**: 작업전 점검이면 BEFORE_WORK 항목만 표시
- 작업자는 주기에 맞는 항목만 봄 → 매일 점검 시 4~5개 수준

## 8. 데이터 품질 이슈

### 8.1 inspection_master 데이터 정합성

- cycle 값 대소문자 혼재: `DAILY` vs `daily`, `MONTHLY` vs `monthly`
  → 정규화 필요 (전부 대문자로 통일)
- 일부 설비 중복: `지게차_전동식`(5항목) + `MFG-011 지게차_전동식`(8항목)
  → 코드 체계 통일 필요
- `is_mandatory` 미설정: 산업 38개 설비 중 11개가 mandatory=0
  → GPT 수집 2차분(12항목짜리)에 mandatory 미설정된 것으로 추정

### 8.2 필요 조치

1. cycle 대문자 정규화
2. 설비 코드 중복 정리 (코드 있는 것 기준으로 병합)
3. mandatory 미설정 항목 검토
