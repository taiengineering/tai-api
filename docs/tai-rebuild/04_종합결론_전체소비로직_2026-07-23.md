## 1. 단일 근본 질환: "엔진 결과 계약"이 없다 → N중 병렬 계약·투영

엔진(블랙박스)이 내는 결과가 **하나의 계약으로 고정되지 않고**, 저장·읽기·투영이 제각기 갈라져 유지보수 불가의 핵심을 이룬다.

### 1-A. 결과 저장이 4곳
`factory_diagnosis_results.result_data`(obligation_adapter 경로) · `quotes.legal_result_json`(견적 기반 리포트) · `anonymous_diagnosis_results`(공개) · `/legal-engine/result/{quote_id}`(즉시 산출). 서로 조인/동기화 코드 없음.

### 1-B. 읽기 계약이 4가지 (프론트가 각각 다른 형태에 강결합)
- **transform 내부계약**(미소비): `{headline, obligations, warnings, roi, inspection_schedule, next_actions}` — 폴백 추측 기계(`diagnosis_transform.py`).
- **admin report-v1**: 원시 `legal.{appointment_required, inspection_required, action_required, report_required}` 배열 + 행키(`law_name, law_article, inspection_cycle, rule_type, penalty_amount…`). **엔진 코드→한글 맵을 클라이언트에서 재현**(`reportModel.ts` `CYCLE_MAP{'003':'월 1회'}`, `RULE_TYPE_KO{'001':'선임 의무'}`, `QUAL_MAP`). → 엔진 코드체계 변경 시 admin 리포트 즉시 깨짐.
- **public**: `/diagnosis/result/{token}` → `rules_table[].obligation_type∈APPOINT/INSPECT/ACTION/REPORT/NOTIFY`, `summary.{…}`, `law_badges[]`. 페이지 내 대형 `MOCK_DATA` 상수로 계약 복제.
- **admin diagnosis-step1**: flat `risk_level, key_obligations[], rules_table[]`.

> 결론: 같은 엔진 산출을 **최소 4개 프론트/백 계약**이 각자 해석. 계약이 코드에 문서화·버전화돼 있지 않아, 한쪽을 고치면 다른 쪽이 조용히 깨진다(엔진 경계의 "고치면 깨짐").

### 1-C. 다운스트림 투영이 3~4개 단절 서브시스템 (status 어휘 상충)
- **일정**: `work_schedules`(2 writer 충돌 — 진단직결 `PENDING` vs 세트기반 `SCHEDULED`) + `runtime_schedule`(별도) + `work_assignments`(지연감시 대상) + inspection_set 일정. `overdue_checker`는 `work_assignments`만 보고 **`runtime_schedule`은 지연감시 누락**. `work_schedules.confirm`은 `created:0` 데드엔드.
- **문서**: 4개 병렬(`document_engine` 레지스트리에 **TBM 1건만** 등록, 나머지 doc_id 404 / `document_engine_api` / `report_forms` / `requirement_engine`). **의무→문서 자동링크 없음**, `generate_document` 동명 엔드포인트 중복. `report-forms/by-factory`는 factory 필터 없이 전량 반환.
- **런타임 태스크**: **두 개의 단절된 런타임 의무 모델** — (A) `runtime_candidate→runtime_task` vs (B) `runtime_obligation_registry→runtime_operational_work_order`. **B에 write하는 코드 미발견 = ghost 의심**(`my-work-orders`가 빈 테이블 조회 가능). `create_task`가 항상 `status="candidate"` 강제(활성화해도 candidate 잔류). candidate/runtime_task/work_schedules/work_assignments **4중 status 어휘 상충**.

## 2. 입력 측(Z1) — 이중 경로 + 정책 모순 + 미검증 배선

- **이중 입력 경로**가 같은 `facility_profiles`에 씀: `facility_profile_api`(구조화, "factories 수정 금지" 명시) vs `exists_input_service.save_exists_inputs`(**factories를 UPDATE** + facility_profiles 신버전). → **정책 모순**.
- 입력 보존·복원·감사(`profile_snapshot` 라운드트립 + `/verify` sc01~03)는 실재하나, `exists_inputs/worker_count`는 감사 비교에서 누락(사각지대).
- **엔진 입력 배선은 이 리포 밖**: 앱은 `obligation_instance`·`semantic_clause`를 **읽기만**(엔진이 write). 사용자 입력 → 엔진(obligation_instance 생성) 사이 실제 투입 코드는 tai-api에 없음 → **검증 불가(엔진 워크스트림 소관)**.
- scope 평가가 `INDUSTRY`만 구현, `PROCESS/EQUIP/ACTIVITY`는 영구 UNKNOWN.

**핸드오프 소유권(확정):** `facility_profiles`·`factories`·`applicability_conditions`·`factory_diagnosis_results` = **앱 소유**; `obligation_instance`·`semantic_clause` = **엔진 write → 앱 read**.

## 3. 순수 SaaS 도메인(Z4) — SSOT 절반, 병렬 저장소 상존

- **가격**: SSOT(`price_master`)는 명목뿐, 병렬 저장소 5+(`price_saas_plan/diagnosis_report/repair_brokerage/safety_management/consulting`, `price_policy`, `product_pricing`, `pricing_key_map`). `pricing_validation_api`는 **여전히 구 소스를 정본으로 검증**(SSOT와 모순). `admin_pricing`이 `public_pricing._cache`를 직접 침범. 감사로그 이원화(`price_change_log`/`pricing_audit_log`).
- **커미션**: **SSOT 없음** — `price_commission`/`connection_commission`(다른 스키마)/`price_repair_brokerage`/`experts.platform_fee_rate` 파편화.
- **수선 vs fix**: **병렬 공급자 레지스트리 2개**(`repair_companies` + `fix_providers`) 동시 생존. `repair`/`fix_chat`이 같은 매칭 테이블에 다른 태그로 write.
- **교육**: 완료이력 이원화(`education_history` vs `education_assignment`), `company-settings` 엔드포인트 중복.
- **점검**: item/schedule 생성기 2개가 `work_schedules`에 병렬 기록, status 대소문자 드리프트(`planned` 읽고 `SCHEDULED` 쓰기).
- **결제**: 여기만 SSOT 깔끔(`payments`/뷰 `v_payments_list`, 단건/정기/운영 분할).

## 4. 교차 결합(Cross-cutting)

- **auth가 진짜 중앙 결합점**: `get_current_user`가 **22개 파일**에서 참조. `service_role`로 전 쿼리 RLS 우회(→ §0 교정). `/login`에 `dev_otp` 노출(미제거 개발코드).
- **system_codes**는 전역 enum SSOT지만 소비자는 소수(saas_core/users/diagnosis_fields 등) — 정작 결제·교육·점검 도메인은 상태값을 **인라인 문자열 하드코딩**(enum 중앙화 미완).
- **알림**: 레거시 `notifications.py`(SITE만 동작, 이메일/카카오/Push=PENDING)가 신형 runtime 알림엔진에 사실상 대체됨. `notification_engine_api`와 `notification_bridge`가 **동일 `runtime_notification_queue`를 중복 변경**(ACK 로직 이중).
- **프론트 전역 복붙**(00 재확인): admin `localStorage['access_token']`+싱글턴 apiClient, public `session.js`+`/_api` 프록시, safe `window.TAI`+`tai_user`. safe는 OTP를 **Supabase Edge Function 직접 호출**로 우회.

## 5. 결론 (통합)

리빌딩의 실패 축은 셋이며, **1번이 압도적 핵심**이다.

1. **엔진 결과 "계약" 부재** → 저장 4·읽기 4·투영 3~4로 파편화, 프론트가 엔진 코드맵을 클라이언트에서 재현 → **엔진/한쪽 수정이 도처를 깬다.** 이건 코드 정리로 못 고치고 **계약(스키마·버전) 도입**으로만 고친다.
2. **앱 계층 복붙 결합**(전역·시크릿·상태문자열·중복 엔드포인트) → 사이트/도메인 간 드리프트.
3. **반쪽 마이그레이션 + SSOT 절반**(가격/커미션/교육/알림 병렬 저장소, 미등록 고아 라우터 ~35, 레거시 프론트 잔존).

**따라서 작업의 무게중심은 "청소"가 아니라 "계약 정립"이다.** 01 계획의 신규 Object로:
- **OBJ-C1(최우선): 엔진 결과 단일 계약 v1** — 저장 4·읽기 4를 **하나의 버전드 result contract**로 수렴, 프론트의 코드→라벨 맵을 백엔드 계약으로 이관, transform을 "추측→검증". 엔진팀과는 **이 계약 버전으로만** 접속.
- **OBJ-C2: 다운스트림 투영 통합** — 일정/문서/런타임의 4중 status 어휘·중복 테이블을 단일 상태기계로. ghost 의심(`runtime_obligation_registry` writer 부재) 확정·정리.
- **OBJ-C3: 입력 경로 단일화** — facility_profiles 이중 write·factories 수정 모순 제거, 엔진 투입 배선을 엔진팀과 계약화.
- **OBJ-C4: SaaS SSOT 완성** — 가격/커미션/교육/알림 병렬 저장소 수렴, pricing_validation SSOT 모순 제거.
- **OBJ-C5: 앱 결합 제거**(기존 OBJ-04와 통합) + **보안**: dev_otp 제거, anon 열람표면 축소(백엔드 무관, 프론트 직결 한정).

## 6. 아직 검증 못 한 것 (정직한 잔여 — 결론 확정 전 필요)
- **엔진 투입 배선**: 사용자 입력 → 엔진(obligation_instance 생성) 실제 경로(45cminc 소관, tai-api 밖).
- **services/*_svc 내부**: `matching_svc`·`document_engine_svc`·`inspection_sets` 서비스가 실제 쓰는 테이블(라우터만으론 미확인).
- **레거시 스택 실배선 여부**: `notifications.py` 등 레거시가 지금도 라우팅되는지, `runtime_obligation_registry` writer 존재 여부.
- `result_data`의 `inspection_required` 등 원시 키의 실제 존재(엔진 산출 스키마).

→ 이 4개는 **엔진팀 인터뷰 1회 + services/ 계층 1차 정독**으로 닫을 수 있으며, 그 전까지 위 결론은 "앱·프론트·DB 실측 기준 확정, 엔진 투입부만 미확정"으로 읽어야 한다.
