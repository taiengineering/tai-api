## 1. 잔여 4항 — 종결

**① 엔진 투입 배선 = HTTP 아님, in-DB RPC + 비권위적 Shadow.**
tai-api의 엔진 인접 코드(`services/check_engine*`, `legal_engine_adapter*`, `obligation_instance_adapter`, `semantic_clause_service`)는 **전부 Supabase(`.table()/.rpc()`)만 호출**, 아웃바운드 HTTP 없음. 핵심: `legal_engine_adapter_run.py`가 `supabase.rpc("diagnose_clauses_common")`(Postgres 함수)로 `semantic_clause`(**58,495행**) 위에서 in-DB 시빙 수행. 유일한 엔진 아웃바운드는 `clients/leg_runtime_client.py`의 `httpx.post(LEG_RUNTIME_URL + "/evaluate")`인데 **Shadow 모드**(`run_shadow_compare`, `LEG_RUNTIME_URL` 미설정 시 `SKIP`, 결과 무영향; `anonymous_diagnosis.py`에서 호출). `ENGINE_URL`/fgw/mcp-gateway 호출 0건.
→ **엔진 경계는 사실상 "DB 계약"**: 테이블(`obligation_instance`·`semantic_clause`·`facility_applicability`) + **Postgres 함수(`diagnose_clauses_common` 등, public 함수 234개 중 일부)**. 즉 엔진 소유 자산에 **DB 함수도 포함** → 앱 DB 정리·계약 설계 시 반드시 고려.

**② Ghost/Writer 확정.**
- `runtime_obligation_registry` = **앱 read-only(진성 ghost)** — insert/update 전무, select만.
- `runtime_operational_work_order` = **update-only**(`my_inspection_bridge`가 상태 전이), INSERT 없음 → 행 생성은 엔진 추정.
- 라이브 런타임 경로는 `runtime_candidate → runtime_task`(둘 다 **339행**, writer=`runtime_task_service` "이 서비스만 candidate에서 runtime_task/schedule 생성").

**③ Services 내부(테이블 R/W) — Z4 공백 해소.**
- `matching_svc`: WRITE `matching_requests`·`matching_results`·`notifications` / READ `matching_contracts`·`price_commission`·`settlements`·`fix_chat_sessions`.
- `document_engine_svc`: WRITE `runtime_document_data`·`generated_document`·`evidence_vault_link`·`runtime_document_approval`·`runtime_lifecycle_audit_log` / READ `runtime_form_schema`·`runtime_field`·`runtime_checklist_item`·뷰 `v_runtime_metrics`.
- `inspection_sets_svc`: WRITE `inspection_sets`·`inspection_set_items`·`work_schedules` / READ `master_building_legal_rules`·`factories`.

**④ 레거시 라우팅.**
- `routers/notifications.py` **여전히 등록**(`router_registry/saas_core.py`). 단 `notifications` 테이블에만 write, 엔진 `notification_engine/queue_manager`는 `runtime_notification_queue`에 write → **물리적 co-write 없음, 기능적 레거시**.
- `routers/legacy_freeze.py` = **능동 폐기 가드**: 레거시 쓰기(`/schedules/legacy-*`, `/documents/legacy-*`, `/diagnosis/legacy-autofill`)에 **HTTP 410 Gone** + 대체 runtime 엔드포인트 안내. 데드코드 아님(좋은 패턴).

## 2. 04 재보정 (실측 반영)

| 04의 서술 | 재보정 |
|---|---|
| 진단 소비 중심 = `factory_diagnosis_results` | **트래픽 반전.** FDR = **2행**(거의 미사용). 실 볼륨은 **`anonymous_diagnosis_results` 3,409행 = 공개/익명 트랙이 실제 제품.** 인증 transform 경로는 사실상 사장. |
| "엔진 결과 계약 부재"(정성) | **정량 실증.** FDR 5행 샘플인데 최상위 키가 행마다 상이(applicable_count 5, obligations 3, verdict 3, appointment_required 1, rules 1, universal 1…). **같은 테이블에 행별 다른 스키마.** |
| 저장 4곳(동급) | **스키마가 서로 다름**: FDR(`obligations/verdict/key_obligations…`) vs `anonymous_diagnosis_results`(`input_data/partial_result/full_result` + `tier_code/paid_amount` 프리미엄 과금) vs `quotes.legal_result_json`. 계약 통일 시 **공개 트랙(full_result)을 1순위**로. |
| 엔진 = 외부(HTTP) 블랙박스 | **하이브리드**: in-DB RPC(권위) + 외부 LEG runtime(현재 Shadow·비권위). 엔진 경계에 **DB 함수 포함**. |

## 3. 결론에의 영향 (01 계획 반영 포인트)
- **C1(엔진 결과 단일 계약)**: 계약 대상이 HTTP 응답이 아니라 **DB 산출(테이블+RPC)**. 통일 계약은 `full_result`(공개, 3409행)를 기준 스키마로 삼고 FDR/legal_result_json을 수렴. transform "추측→검증"은 이 계약 위에서.
- **C2(다운스트림 투영)**: 라이브는 `runtime_candidate→runtime_task`(339). `runtime_obligation_registry`(ghost)·`runtime_operational_work_order`(엔진 update-only)는 엔진 소유로 분류 → 앱 정리 대상 아님.
- **엔진 워크스트림 경계 확장**: 엔진 소유 = 테이블 계열(semantic_clause 58k 등) **+ Postgres 함수(diagnose_clauses_common 등)**. 앱 DB 정리(OBJ-07)는 이 함수군도 제외.
- **우선순위 재조정**: 인증 진단 UI(FDR·transform, 2행)보다 **공개 진단 트랙(anonymous_diagnosis_results, 과금 포함)** 이 제품의 핵심 → 계약·리빌딩 우선순위 상향.

*04 §6의 미검증 4항은 본 문서로 종결. 유일 잔여 = 엔진 내부(LEG runtime 31,434 atom 시빙, `diagnose_clauses_common` 함수 본문) — 명시적 black box(엔진 워크스트림 소관).*
