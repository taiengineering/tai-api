## 0. 한 줄 진단

세 사이트를 3계층으로 나눴지만, **경계(전역변수·DB 테이블 이름)가 계약이 아니라 "복사된 구현"으로 연결**돼 있어, 계층/사이트가 물리적으로만 분리됐고 논리적으로는 여전히 한 덩어리다. 여기에 **원자적이지 않은 리팩터링**(DB만 먼저 이관, API·프론트는 잔존)과 **엔진 18차 재개발의 잔재**가 겹쳐, 수정이 국소화되지 않고 비가용 자산이 누적됐다.

## 2. 근본 원인

### 근본원인 A — 공유가 아니라 "복사된" 전역변수 (핵심 통증)

3계층으로 나눴어도 **사이트 간 경계가 `window` 전역과 하드코딩 시크릿의 복붙**으로 이어져 있어, 한 파일을 고치면 나머지 복사본이 어긋난다.

**증거**
- `admin/full-version/assets/js/tai/supabase-config.js` — 전역 `TAI_SUPABASE{URL,ANON_KEY}`, `sbHeaders()`, `sbFetch()`. Supabase URL + anon JWT(`eyJ…AenP48`) 하드코딩.
- `admin/full-version/assets/js/tai/api.js` — 전역 `TAI_API`, `apiCall()`; `globals.js` — `G`, `loadGlobals`, `fillSelect`, `renderPagination`.
- **admin 안에 anon 키가 2종 공존**: `admin/full-version/config.js`는 `CONFIG.SUPABASE_ANON_KEY = sb_publishable_r0qsGe8…`(퍼블리셔블 키)로, `supabase-config.js`의 JWT와 **다른 키**.
- **safe(tadmin)는 공유가 아니라 분기된 복사본**: `tadmin/full-version/assets/js/tai/api.js`는 12초 타임아웃·`apiCallAll` 추가 + 401 리다이렉트가 **상대경로**(admin은 절대경로) / `globals.js`도 `loadGlobals` 응답 처리 방식이 다름 / Supabase 결합은 `tadmin/full-version/app/_utils.js`에서 별도 전역 `TAI`·`apiFetch`로 재하드코딩.
- **tai-www도 같은 키 복붙**: `public/scripts/inquiry-form.js`가 `vwlahtguyggrhvslabax.supabase.co/rest/v1/inquiries`에 **동일 anon JWT**로 직접 쓰기. 헤더에 "nexas/… / safe와 동일"이라 적혀 있고 `source ∈ ['marketing','safe']` → **공개사이트와 safe가 같은 파일·같은 키·같은 `inquiries` 테이블을 공유**.
- 신규 `admin-vue3`는 전역을 composable(`useTaiApi`·`useSupabaseRest.sbFetch`·`useApiError`)로 대체했으나, **anon 키는 여전히 `useSupabaseRest.ts`에 하드코딩**(env 미이관).

**왜 깨지나:** `apiCall`·`sbFetch`·`G`·`TAI_API` 같은 **동일 이름의 독립 복사본**이 5개 이상 파일/2개 사이트에 존재. 시그니처(타임아웃, 401 경로), `system-codes` 카테고리 명, anon 키 회전 중 **하나만 고치면 나머지가 어긋난다**. 이미 admin↔tadmin에서 드리프트가 발생.

### 근본원인 B — 계층 간 SSOT/뷰 결합 (원자적이지 않은 리팩터링)

가격 도메인을 `price_master`(+`price_service_feature`) 단일 SSOT로 이관했지만 **DB만 먼저 바꾸고 API·프론트는 옛 이름을 계속 참조**해, 한 계층 수정이 다른 계층을 깨뜨렸다.

**증거**
- 의도된 SSOT: `routers/price_master_admin.py`(`/price-master`), `routers/public_pricing.py`(v3.0.0, price_master로 정상 이관).
- 그러나 `sql/20260605_archive_legacy_price_tables.sql`가 `price_saas_plan`·`price_diagnosis_report`·`price_quotes`·`price_standard_wage`를 archive로 옮긴 뒤에도 **`price_setting.py`(`/saas-plans`,`/diagnosis-reports`)·`admin_pricing.py`·`pricing_validation_api.py`가 사라진 테이블을 계속 조회** → 라이브 500/"Failed to fetch".
- 특히 `pricing_validation_api.py`의 docstring은 "Single Pricing Source: price_saas_plan + price_diagnosis_report"라고 **틀린 SSOT를 선언** — SSOT가 문서·코드·DB에서 서로 모순.
- 결과적으로 **가격 저장소가 4계열 병존**: price_master / product_pricing(자체 테이블) / price_policy(자체 테이블) / price_commission. SSOT는 7개 라우터 중 2개에서만 강제됨.
- **이번 세션의 대증요법이 곧 이 문제의 표본**: `price_saas_plan`·`price_diagnosis_report`를 price_master 위 **호환 뷰**로 되살려 화면을 복구했다. 뷰는 "옛 이름에 계속 name-coupling된 프론트"를 임시로 붙여주는 반창고이며, 근본 결합은 그대로다(그래서 편집 저장 PATCH는 여전히 안 됨).

### 근본원인 C — 엔진 18차 재개발의 잔재 + 미등록 코드의 침묵사

**증거**
- `tai-api/main.py`(v6.0.2)는 개별 라우터를 직접 등록하지 않고 `router_registry/`의 **10개 그룹 스펙**(`saas_core, legal_engine, document_engine, runtime_bridge, inspection, payment, public, diagnosis, construction, external`)만 로드. → **어느 그룹 목록에도 없는 라우터는 조용히 죽은 코드**가 된다. `routers/` ~170, `services/` ~130.
- 구 엔진 잔재가 `services/`에 그대로: `legal_engine_svc.py`, `legal_engine_v202604.py`, `legal_v510_svc.py`(+커밋된 `.bak`), 다수 어댑터(`legal_engine_adapter*`, `rule_v2_adapter`), 버전 라우터 4종(`legal_engine.py`,`legal_engine_patch.py`,`legal_engine_v510.py`,`engine_legal.py`).
- 재개발 엔진은 `45cminc/*` ~30개 repo 페더레이션(`leg`,`collection-engine`,`engine-manager`,`prediction`,`check`,`adp`,`anl`,`federation-input-engine`,`fgw`,`doc`,`ntf`…). `45cminc/leg`에 `docs/2026-06-11_LEGAL_ENGINE_V4_LAYER_REDESIGN` + `WO_LEG_V4_001_PHASE0` + 100+개의 날짜별 `*_AUDIT/_RESTORATION` 문서 → **여러 차수의 덮어쓰기 흔적**.
- `_archive/routers_20260608/`에 은퇴 라우터 ~24개(`watch_engine_*`×14, `factory_process`/`_v2` 등) — 그런데 `routers/factory_process_v3.py`는 라이브. `pricing_validation_api.py`는 **어느 그룹에도 없는 유령 라우터**.
- DB에도 세대 잔재: `master_legal_rules_*`(구) 3 + `master_rule*`(신) 10, `runtime_*` 98개, `*candidate*` 35개, 0행/미분석 382개.

### (부수) 라우트 순서 버그
- 단일 세그먼트 `GET /{id}` 캐치올(`product_pricing.py`,`price_master_admin.py`)이 형제 라우트 `/summary`·`/overview`를 삼킴. **이미 `/equipment-assets/overview`가 이 버그로 깨져 재구현**했다.

## 3. 보안 표면 (별도 강조)

- 공개 프론트(tai-www·safe)에 **하드코딩된 anon 키**로 현재 **338개 테이블 조회 가능**. 그중 상당수가 엔진 내부 테이블(candidate/runtime/law/residual)로, 대량 `USING(true)` anon SELECT 정책 + grant가 무분별하게 적용된 결과로 보임.
- 동시에 **정책은 열렸는데 grant가 없는 불일치 264개** → 반대로 조회가 42501로 깨진다(kin-management·price-setting과 동일 원인).
- 즉 **정책/GRANT 계층이 상호 불일치**한 채 방치 → 데이터 계층의 "한 곳 고치면 다른 곳 깨짐". anon 키 노출 + 광범위 grant는 회전 리스크와 정보노출 리스크를 동시에 안고 있다.

## 5. 해결책 (우선순위별 로드맵)

### P0 — 지금의 출혈 멈추기 (며칠 단위, 되돌림 가능)
1. **가격 SSOT 컷오버 마감**: `price_setting.py`·`admin_pricing.py`·`pricing_validation_api.py`를 price_master로 재배선하거나 은퇴. 잘못된 SSOT docstring 수정. 임시 호환 뷰는 "제거 티켓"으로 추적.
2. **정책/GRANT 불일치 264개 정합화**: 각 테이블의 *의도된 노출* 결정 → 공개 필요분만 남기고 나머지 anon REVOKE + 정책 축소. 열람 표면 338 → 최소.
3. **라우트 순서 린트**: 단일 세그먼트 `/{id}` 캐치올을 맨 뒤로, 형제 라우트 우선 등록을 CI로 강제.

### P1 — 결합 끊기 (수 주, 근본 원인)
4. **전역 복붙 제거 → 단일 공유 클라이언트 패키지** `@tai/client`(설정+`apiCall`+`sbFetch`+세션 계약)를 3사이트가 import. `window` 전역·복사본 폐기.
5. **시크릿을 소스에서 제거**: URL/anon 키·API base를 env/빌드타임 주입, 단일 출처. admin 2번째 키 제거, 노출된 anon 키 회전.
6. **계약 우선(contract-first)**: 경계를 DB 테이블 모양이 아닌 API 계약(OpenAPI)으로. 뷰는 API 내부 read-model로만.
7. **마이그레이션 마감**: safe(tadmin) 재빌드 + admin 잔여 ~10p 완료 후 `admin/full-version` 은퇴.

### P2 — 비가용 자산 정리 (지속)
8. **DB 스윕**: 0행/미참조 382개 분류 → archive 격리, 규칙 2세대·초안계열 통합.
9. **백엔드 정리**: `_archive`·`*.bak`·구 `legal_*_v*` 삭제, `router_registry` 단일 매니페스트 보증(미등록=삭제).
10. **프론트 정리**: 중복 트리·벤더·이중 프록시 제거.
11. **재발 방지 CI 게이트**: 미등록 라우터/ 정책≠GRANT/ 프론트 테이블 직접참조/ 하드코딩 시크릿 → 빌드 실패.

### 프로세스 원칙 (거버넌스)
- **원자적 마이그레이션**(DB+API+FE 조율 또는 expand/contract, 호환 뷰는 추적되는 임시물).
- **도메인당 SSOT 1개**. **시크릿은 env, 소스 금지**.
