# TAI 문서엔진 전체 기획서 (Master Plan) v1

> 작성일: 2026-08-22
> 상태: 기획 초안 (operator 검토용)
> 성격: 이번까지의 조사·확정을 하나의 흐름으로 엮은 상위 기획서.
> 하위 정본: DOCUMENT_CODE_CONVENTION_v1(코드 규정) · DOCUMENT_ENGINE_CURRENT_STATUS_v1(현황) · DOCUMENT_STANDARD_SOURCES_v1(표준 소스). 충돌 시 각 하위 정본 우선, 본 문서는 흐름을 정의한다.

---

## 1. 목적과 철학

**한 문장 골: 안전관리자가 매일 직접 점검한 데이터가, 필요한 시점에 법정 문서로 자동 렌더링되어 나온다.**

- 빈 양식을 파는 게 아니다. 점검하는 행위 자체가 문서가 된다.
- 문서 실물을 쌓지 않는다. DB엔 제목·조건만 두고, 출력할 때 렌더링한다(자원 절약).
- 판단하지 않는다. 데이터를 모아 정해진 템플릿에 주입할 뿐, 법 해석은 하지 않는다.

## 2. 운영 전제 (관점 확정)

- 안전관리자 1인이 시설·공정·설비를 등록하고, 점검 주기를 설정하고, **배당 없이 직접 점검**한다.
- 따라서 데이터 소스가 한 사람으로 단순하다 → 문서엔진에 유리하다.
- **점검 주기 설정 = 문서 발생 스케줄**이다.

## 3. 현재 상태 (실측 요약)

| 자산 | 상태 |
|---|---|
| 렌더 엔진(renderer: Jinja2→Gotenberg) | 완전 구현 |
| 검증된 레퍼런스(compliance_report: 운영데이터→PDF) | 완전 동작 |
| 데이터 패처 | inspection·tbm 2종 (education 미구현) |
| 완성 템플릿 | 2건뿐 (DOC-OSH-056, DOC-COMPLIANCE-REPORT) |

**격차**: 법이 요구 253건 / 자동화 가능 214건 / 즉시가용(데이터 준비) 25건 / 실제 생성 가능 2건. 비어 있는 것은 오직 **렌더 템플릿**이다.

## 4. 문서 분류 (조사 결과)

- 전체 카탈로그 260건(document_forms): 등급 A30/B75/C72/D37/X46.
- 즉시가용 A등급 30건은 실제로 **8개 유형으로 수렴**: INSP(안전점검일지)·CHK(체크리스트)·EQUIP(설비점검)·TBM·PPE(보호구)·CONLOG(공사일지)·APPT(선임)·EDU(교육, 보류).
- 설비점검(EQUIP) 15건은 "구조는 같고 대상만 다른" 하나의 유형 + 세부(ELEC·GAS·ELEV…).

## 5. 표준 소스 (3계층)

1. 법정 별지 서식(양식 법 고정) → 국가법령정보센터. 관공서 제출(D등급).
2. KOSHA 표준 서식 → KRAS·서식자료. 위험성평가·관리규정(C등급).
3. 필수 기재사항만 법정(양식 자유) → 내부 kosha_guide_body(1,031건 적재) + 법조문. 점검·TBM(A등급).

## 6. 코드 규정 (두 층위)

- 층위 1 서식 유형: `DOC-{TYPE}` (유형 8종, 안정 식별자, 날짜 없음).
- 층위 2 발행 문서: `{TYPE}-{사업장}-{YYYYMMDD}[-{세부}]`. 세부는 날짜 뒤에만.
- 원칙: 코드는 식별자, 분류(섹터·등급·법근거)는 컬럼. 화면 제목은 별도 한글.
- 상세: DOCUMENT_CODE_CONVENTION_v1.

## 7. 매핑 설계 (두 겹) — 핵심

```
문서(doc_id 260) ──1겹──▶ 코드체계(TYPE·DETAIL) ──2겹──▶ 템플릿(DOC-{TYPE}.html)+fetcher
   행마다(DB 컬럼)           유형 8 / 세부 12          유형마다(레지스트리 8행)
```

- **1겹 (문서↔코드)**: 각 doc_id를 TYPE·DETAIL로 분류. 데이터라서 document_forms의 컬럼(TYPE·DETAIL)에 저장. 260행 규모, 조사·법령에 따라 변동.
- **2겹 (유형↔템플릿)**: 각 TYPE이 어느 렌더 템플릿·어느 fetcher로 출력되는지 연결. 유형 8개 규모, 거의 불변. 작은 레지스트리.
- 분리 이유: 두 매핑은 규모(260 vs 8)와 변동 속도가 다르다. 섞으면 유형 하나 바꿀 때 260행을 건드리게 된다.

## 8. 문서 생명주기 (두 종류)

- **생성형 문서**(점검일지·TBM 등): 발행 시 실물 저장 안 함. 호출 시 그 시점 데이터로 렌더링. 매번 최신.
- **확정본 문서**(과거 제출·확정본): 그 시점에 고정된 사실. 발행 코드로 문서함에 쌓되 **그때 PDF/원본을 스냅샷 보관**(storage_ref). eng:DOC 디지털화로 편입 가능.
- 문서함 화면: 유형으로 필터, 제목의 날짜로 시점 구분. 생성형=출력하기(렌더링), 확정본=보기/다운로드(스냅샷).

## 9. 문서가 필요한 시점 (세 트리거)

- **반복(주기)**: 설정한 점검 주기 → 문서 발생. 일일 점검일지·TBM, 월 설비점검·협의체, 연 위험성평가·소방점검.
- **이벤트**: 위험작업 착수→작업허가서, 사고→산재조사표, 신규채용→보호구대장.
- **감사 대응**: 평소 기록을 묶어 중대재해법 경영책임자 입증자료로.

## 10. 렌더 흐름 (검증된 경로)

```
발행 요청(TYPE+사업장+기간) → 2겹으로 템플릿·fetcher 조회
  → fetcher가 운영데이터 조립 → 템플릿 렌더 → Gotenberg PDF
```
compliance_report가 이 경로(fetch→render→PDF)를 이미 검증. 2겹 레지스트리가 서면 유형이 늘어도 코드 수정 없이 확장.

## 11. 구현 로드맵

| 단계 | 내용 | 상태 |
|---|---|---|
| 0 | 코드 규정 확정 | ✅ 완료(v1) |
| 1 | 소스 데이터 구조 실측(inspection 계열) — 2겹 fetcher 근거 | 대기 |
| 2 | 1겹 매핑: document_forms에 TYPE·DETAIL 컬럼 추가·채우기 (A등급 30건 우선) | 대기 |
| 3 | 2겹 매핑: 유형→템플릿·fetcher 레지스트리(8행) | 대기 |
| 4 | 생성 경로 배선: document_forms에 /preview·/generate 추가(compliance_report 패턴 일반화) | 대기 |
| 5 | 템플릿 대량 제작: 즉시가용 유형부터(INSP·EQUIP·TBM·CHK·PPE) | 대기 |
| 6 | 확정본 스냅샷 보관(storage_ref) + 문서함 화면 | 대기 |
| 7 | B·C·D 등급 확장 | 대기 |

원칙: 각 단계는 실측→검증 후 다음. A등급 즉시가용에서 방식을 검증한 뒤 확장(폭주 금지).

## 12. operator 결정/확인 필요

- 매핑 저장 위치: document_forms 컬럼 추가(권고) vs 별도 매핑 테이블.
- 세 테이블(카탈로그·법정별지·마스터) 물리 통합 vs 매핑 참조.
- EQUIP 유형 1템플릿+대상 데이터 주입 성립 여부(대상별 점검항목 데이터 관리 실측 — 단계 1).
- 교육(EDU) 재개 시점(교육 모듈 가동 조건).
