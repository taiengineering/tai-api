# 문서엔진 아키텍처 결정 (Architecture Decisions) v1

> 작성일: 2026-08-22
> 성격: 부하·저장·무결성 논의의 확정 결정 기록(ADR). 이후 설계·구현의 기준선.
> 배경: 오픈 전. 데이터는 전부 목업(행 수는 오판 유발, 판단은 증식 메커니즘으로).

---

## 작업 방식 (D-00)
- **오브젝트 방식**(수직): 문서 유형 하나를 DB부터 배선까지 완결·검증하고 "더 작업 없음" 확인 후 패스. 단계별(수평) MVP 금지.
- pass 못 하면 다음으로 넘어가지 않는다. 검증 모듈은 재사용(오브젝트마다 수작업 반복 금지).
- 검증은 PDF 직전까지 이 환경에서, PDF 렌더는 operator 터미널에서 함께.

## 문서 생명주기 (D-01)
- 트리거(수동/자동) → 문서 발행 → **웹뷰(HTML)로 조회·수정·저장**(반복) → 출력 버튼 → PDF 다운로드.
- 웹뷰가 주(主), PDF는 종(從). renderer의 render_document_html(웹뷰)·generate_document_pdf(출력)로 이미 분리됨.

## lazy 저장 (D-02)
- **문서 본체는 저장하지 않는다.** 점검 기록이 곧 문서의 소스. 조회 시점에 유형을 얹어 조립.
- 규모 근거: 100업체 × 100장/일 = 연 3,650만 장. 저장하면 원본의 사본이 수억 행 → 낭비. lazy면 행 0.

## 전표 방식 (D-03)
- 원본(점검 기록)은 불변. 수정은 덮어쓰기가 아니라 **새 전표(변경분 델타) append**. 과거 전표는 이력으로 남음.
- 조회 = 원본 + 시점순 전표를 접어 현재값. 무결성(소급 불변)과 편의성(수정 자유) 동시 만족.
- 변경 없는 다수 = 전표 0. 변경된 소수만 전표. lazy와 전표가 여기서 화해.

## 저장 대상 = 예외만 (D-04)
- 문서 본체 테이블 **없음**.
- **편집분 테이블**: 수정된 것만(변경 필드 델타, append-only).
- **확정 스냅샷 테이블**: 확정한 것만(그 시점 데이터 봉인).
- 문서 목록 = safety_inspections + 유형 매핑 조인(뷰/쿼리). 별도 저장 없음.

## 확정 봉인 (D-05)
- 봉인은 **사용자가 "확정 출력"을 누를 때만**. 자동·강제 봉인 없음.
- 근거: 현실의 점검은 상당수 요식행위. 무결성을 시스템이 강제하면 우회당하고 버려진다(이커머스 교훈). "중요하면 확정 누르세요"가 정직한 선. 편의성 제공이 채택의 핵심.
- 점검 기록 자체의 불변성 강제도 **안 함**(같은 이유).

## 부하 = 파티셔닝 (D-06)
- 물리 테이블 분리(업체별 테이블) **금지** — 100개는 되나 확장 시 pg_class 폭증·마이그레이션 지옥(60개서 5초→5분).
- **Postgres 네이티브 파티셔닝** 채택. 사업장 단위 조회 결정 → **파티션 키 = factory_id**. 파티션 프루닝으로 "자기 것만 스캔" 자동.
- 규모 기준: 100~5,000 테넌트 = 파티셔닝 sweet spot.

## 파티션 타이밍 (D-07)
- **지금(오픈 전, 목업)이 유일한 공짜 창.** 데이터 이사 0, 다운타임 0.
- 나중 전환은 대수술: 기존 테이블 직접 파티션 불가 → 새 테이블+데이터 이전, 트랜잭션 실패·정합·스토리지 2배·트리거 누락 위험. 오픈 후엔 이 창이 닫힘.
- 최소 필수: 새 테이블은 factory_id + 파티션 호환 스키마로 설계(나중 ATTACH 대비).

## 파티션 대상 (D-08)
- 대상 = **점검 스케줄(work_schedules) + 문서(새 편집분·확정본)**. factory_id 축.
- 제외: 마스터·설정(factories·users·equipment_assets·설정류 — 실체당 고정).
- inspection_sets는 증식 약함(정의는 고정) → 대상 아님. child(safety_inspection_results·tbm_attendees)는 부모 따라감.
- 선결: safety_inspections·work_assignments·child에 factory_id 부재 → 파티션 키 확보 필요.

## 문서 저장 방식 = B (D-09)
- 기존 문서 저장 3계열(generated_document·documents·runtime_document_data)은 **레거시로 격리**(건드리지 않음, 물린 기능은 유지).
- 파티션·저장 대상 "문서" = 이 레거시가 아니라 **새로 정의할 편집분·확정본 저장소**.
- 근거: 세 계열 전부 "문서 통째 저장" 방식 = lazy와 충돌. 부하 논의(D-02) 일관성 위해 B.

## PDF 저장 (D-10)
- DB에 PDF 바이너리 저장 **금지**.
- 살아있는 문서 PDF: 저장 안 함, 요청 시 on-the-fly 생성.
- 확정본 PDF: **오브젝트 스토리지 파일**(S3/R2류) + DB엔 참조(키)만.

## 로그 (D-11)
- SaaS는 인프라 로그(장애·성능) + 감사 로그(변경 이력) 둘 다 필요.
- 실측: 감사 로그는 이미 과잉(로그성 테이블 72개, audit 20+). 인프라 로그는 pgaudit 없음(Supabase 기본만, 단기).
- 로그 파티션 축 = **날짜**(factory_id 아님). 핫/콜드 분리 → 오래된 파티션은 스토리지 아카이브 후 DROP.
- pgaudit는 초기 과함. 기본 로그 + pg_stat_statements로 운영, 장기보관은 외부 export.

## 별건 (D-12)
- **로그 통합**: 72개 파편화 → 별도 프로젝트. 오픈 전이 적기. 파티션 구조로 자리 예약.
- **type_code 정비**: equipment_type_code 목업 혼재. 단 법령진단 엔진 34곳 입력이라 삭제·격리 불가. 설비 마스터 데이터 정비로 값만 정합화(설비자산 도메인).

## 미해결 선결과제 (D-13) — 다음 조사
- **점검 기록 → 문서 유형 매핑이 성립 안 됨.** inspection_sets.category 0건, work_assignments→set 연결 0건, safety_inspections.asset_id null.
- B(lazy)는 조회 시점에 유형을 얹어야 하므로 이 매핑이 필수 전제. 안 되면 편집분·확정본을 파티션해도 조회 목록이 안 나온다.
- 다음: inspection_sets가 실제 어느 축(category·legal_rule·set_name·template_id)에 값을 갖는지 실측 → 매핑 규칙 설계.
