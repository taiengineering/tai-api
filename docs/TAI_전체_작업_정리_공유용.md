# TAI 전체 작업 정리 (공유용)

> **참조용**: 다른 세션·창·에이전트에서 TAI 제품·아키텍처 방향을 맞출 때 이 문서를 우선 확인한다.  
> 저장소 경로: `tai-api/docs/TAI_전체_작업_정리_공유용.md`

---

## 1. 서비스 핵심 구조

TAI는 단순 SaaS가 아니라 다음 구조를 가진다.

**진단 → Task 생성 → 요청 → 매칭 → 계약 → 수행 → 관리 → 반복**

즉,

- 문제를 만들어내고
- 실행을 연결하고
- 이후 관리까지 이어지는 시스템

---

## 2. 무료진단 → 전환 구조

**핵심 원칙**

- 진단은 로그인 없이 시작
- 결과 일부를 먼저 보여줌
- 전체 결과에서 로그인 유도
- 로그인 후 원래 결과로 복귀

**구현 핵심**

- `anonymous_diagnosis_results` 테이블 생성
- `public_token` 발급
- `localStorage`로 redirect 유지
- 로그인 후 token으로 결과 복원

---

## 3. 법령엔진 구조 문제

**핵심 문제**

1. 문장 기반 데이터 → 판단 구조 부족
2. sector 필터 일관성 부족
3. stage 구조 미완성
4. Task 개념 없음
5. 실행 메타데이터 부족
6. 복합 조건 처리 한계
7. 중복 제거를 코드에 의존
8. 수집 데이터와 판단 데이터 미분리

**핵심 해결 방향**

- 법령 원문 / 판단 데이터 분리
- Task 중심 구조 도입
- 메타데이터 표준화
- 복합 조건 구조 개선
- 데이터 기반 정규화

---

## 4. 어드민 구조 설계

**핵심 원칙**

- 메뉴 = 업무  
- 진행 = state  

즉,

- CRUD 구조 ❌  
- Case 상태 기반 시스템 ✔  

---

## 5. 어드민 메뉴 구조

1. 대시보드  
2. 법령진단  
3. 선임  
4. 위험성평가  
5. 정기점검  
6. 계획문서  
7. 수선/시공  
8. 파트너  
9. 결제/정산  
10. 알림/운영  

---

## 6. 상태 기반 운영 구조

**예: 선임**

- `REQUESTED`
- `MATCHING`
- `QUOTING`
- `WAITING_APPROVAL`
- `CONTRACTED`
- `IN_PROGRESS`
- `COMPLETED`
- `CANCELLED`

**핵심**: 하나의 페이지에서 state로 전체 흐름 제어

---

## 7. 공통 Case 구조

Case는 다음을 포함해야 함:

- 기본정보
- 진단 결과
- Task
- 매칭
- 견적
- 계약
- 진행 상태
- 문서
- 알림
- 로그

---

## 8. Task 중심 구조

**핵심 흐름**: 진단 → Task → Case

**Task 구조**

- `task_type`
- `source_type`
- `due_date`
- `status`
- `priority`

---

## 9. 대시보드 구조

- 단순 요약 ❌  
- 비즈니스 관제 ✔  

**표시 항목**

- 진단 수
- Task 수
- 요청 수
- 계약 수
- SaaS 전환
- 파트너 응답률

**퍼널**: 진단 → Task → 요청 → 계약 → SaaS

---

## 10. 파트너 구조

파트너는 사용자가 아니다.

**파트너 = 공급망**

**구조**

- 신청
- 승인
- 유형별 관리
- 성과 관리

---

## 11. 마이페이지 구조

**구조**

- 일반 사용자 → 기본 마이페이지
- 파트너 신청 → 상태 관리
- 승인 후 → 파트너 메뉴 확장

**핵심**: 상태 기반 UI

---

## 12. 프라이싱 전략

- 입력 단계 ❌  
- 결과 이후 ✔  

**구조**

- SaaS 시작
- 프리미엄 진단
- 실행 요청

가격은 **설득 후** 노출

---

## 13. 전체 핵심 정리

TAI는 다음 시스템이다:

- 법령 기반 **문제 생성** 시스템
- Task 기반 **실행 연결** 시스템
- SaaS 기반 **관리** 시스템

---

## 14. 최종 한 줄

메뉴는 업무로 나누고  
진행은 state로 통제하며  
데이터는 판단 가능한 구조로 재정의해야 한다
