## 2. 서버 인프라 전환 전략 (100% 완료 후)

### 현재 문제점
- Railway 서버가 물리적으로 멀어(싱가포르/미국) 한국 레이턴시 100~150ms
- 캐싱 미사용
- Vuexy 템플릿 부분 활용

### 전환 검토 옵션 (우선순위)
1. **Fly.io 도쿄** — Railway 유사 DX, 한국 레이턴시 25~35ms, PaaS라 서버 관리 불필요
2. **AWS Lightsail 서울** — 최저 레이턴시 3~8ms, 서버 직접관리 부담
3. **NCP** — B2G CSAP 가산점, 비용 높음

### Fly.io 이전 예상 소요
- **반나절** (4~5시간)
- Dockerfile + fly.toml 작성 → 환경변수 복사 → 도쿄 배포 → DNS 전환
- DB(Supabase), 프론트(Cloudflare Pages), 코드(GitHub) 변경 없음
- 다운타임 사실상 0 (Cloudflare CNAME 변경)

## 3. 하이브리드 아키텍처 계획 (100% 완료 후)

### FastAPI를 완전 제거할 수 없는 이유
- **PDF 생성** (wkhtmltopdf → Gotenberg) — Edge Function에서 불가
- **법령엔진 배치 처리** — Python 환경이 생산성 높음

### 전환 구조
| 영역 | 현재 (FastAPI) | 전환 후 |
|------|---------------|--------|
| CRUD (15개+ 라우터) | FastAPI 경유 | **PostgREST + RLS 직접 호출** (서버 비용 $0) |
| 인증 | 자체 JWT | **Supabase Auth** |
| 알림 발송 (SMS/카카오) | FastAPI | **Supabase Edge Function** |
| Cron 작업 | Railway cron (405 오류 중) | **pg_cron** |
| PDF 생성 | wkhtmltopdf | **Gotenberg** (Docker, ~$5/월) |
| 법령엔진 배치 | FastAPI | **FastAPI 유지** (경량화, ~$5~10/월) |
| 캐싱 | 없음 | **Upstash Redis 도쿄** |

### 기능별 Supabase 대체 판정
- 완전 대체 가능: 6개 (CRUD, 인증, 알림, AI룰생성, 파일저장, Cron)
- 조건부 가능: 2개 (법령엔진, 스케줄엔진)
- 대체 불가: 1개 (PDF 생성)

## 6. PDF 생성 전환 (100% 완료 후)

### 현재 문제
- wkhtmltopdf는 2012년 WebKit 엔진 → 최신 CSS 렌더링 불가 → 웹 화면과 PDF 불일치

### 해결: Gotenberg
- 오픈소스 Docker 기반 PDF API
- 실제 Chromium 사용 → 웹 화면과 100% 동일한 PDF
- HTML 보내면 PDF 반환하는 단순한 API
- Railway 또는 Fly.io에 별도 서비스로 배포 (~$5/월)
- 한글 폰트: 커스텀 Dockerfile에 Noto Sans KR 추가
- 63+개 서식(신고서식, 점검일지, 교육기록) 모두 적용
- 기존 HTML 템플릿 그대로 유지, API 호출만 변경

## 7. 웹사이트 디자인 전략

### 현재 문제 진단
1. 한 페이지에서 6가지를 동시에 말하고 있음 (히어로 슬라이더 6개)
2. 톤이 섞여 있음 (위협/친근/도발/비전이 한 페이지에)
3. 히어로 이미지 빈 src
4. AI 코딩만으로는 디자인 퀄리티 한계

### 역할 기반 접근 — 대표 판단 확인
- **안전관리자**: "당신의 업무를 줄여드립니다" (자동일정, 서류생성, 업무분산)
- **현장소장/사업주**: "당신의 리스크를 줄여드립니다" (위험도 대시보드, 법적 증거, 전문가 연결)
- 이 두 메시지를 한 페이지에 섞으면 둘 다 흐려짐
- **역할 기반 접근은 무모한 도전이 아님** — B2B에서 검증된 방식 (Salesforce, HubSpot, 채널톡)
- 소규모 SaaS가 안 하는 이유는 "틀려서"가 아니라 할 여력이 없어서

### 실행 방법
- Framer 검토했으나 그래픽 도구에 가까워 시간 소비 우려 → **Claude + Cursor로 진행** 결정
- **핵심 변경점**: 이전처럼 "해줘"가 아니라, **디자이너에게 지시하듯** 레퍼런스 + 특징 + 구조 설명 + 검수 방식
- 레퍼런스 사이트 2~3개 수집 → 콘텐츠 구조 확정 → 섹션 단위 작업 + 검수

### 메인 페이지 권장 구조
| 순서 | 섹션 | 역할 |
|------|------|------|
| 1 | 히어로 (고정 1개, 슬라이더 아님) | 핵심 메시지 + CTA 1개 + 제품 스크린샷 |
| 2 | 역할 선택 | "안전관리자이신가요?" / "사업장 책임자이신가요?" |
| 3 | 신뢰 지표 | 10억 벌금 / 347% 적발 / 3분 진단 |
| 4 | 3단계 작동 방식 | 진단 → 배정 → 기록 |
| 5 | 대상별 카드 | 건물 / 공장 / 건설 |
| 6 | CTA | 무료 진단 |

### 중기 (6~18개월, 고객 30→200) — 3~4명
| 역할 | 담당 | 업무 |
|------|------|------|
| 대표 | 심태왕 | B2G 조달, 파트너십, 교육사업 기획 |
| 영업/고객 성공 1명 | 정규 | 데모, 고객 관리, 피드백 수집 (월 250~350만원) |
| 개발자 1명 | 상황에 따라 | 서버 안정성, 설비모델/위험예측 개발 (월 매출 1000만+ 시 검토) |
| 교육 콘텐츠/강사 | 외주 | 법정 교육 콘텐츠 제작 (건당 or 파트타임) |

### 채용 타이밍 기준
- 파트타임: 고객 10개 초과 시
- 정규 영업: 월 매출 200~300만원 이상 시
- 개발자: AI로 안 되는 병목이 반복 시
- 교육 사업: 플랫폼 고객 50개 이상, 안정화 후

### 핵심 인사이트
- **첫 채용은 개발자가 아니라 영업/고객 담당**
- 산업안전 시장은 고객이 스스로 찾아오지 않음 → 찾아가야 함
- 대표의 시간 60~70%를 영업에 써야 하며, 이를 위해 운영 지원이 필요
- 제품은 AI가 유지 가능, 고객은 사람이 데려와야 함
